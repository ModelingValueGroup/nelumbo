Types & functors

Before any logic, Nelumbo lets you define syntax: which phrases exist and how they are built. Person :: Object declares a type and Male :: Person a subtype. Male ::= Piet, Jan declares constants of a type. A functor declares a new phrase with ::=: Person ::= father(<Person>) says that father(a person) is itself a person, where each <T> is a hole for an expression of type T. A phrase whose type extends Root can stand on its own line as a sentence; give such a functor the precedence #0. These sections have no queries and no meaning yet: a sentence is correct when it parses, and the editor underlines it in red when it does not.

Patterns

    
A functor's pattern is more than words and holes. <(> really <)?> is
       optional, <(> likes <|> loves <)> is a choice, and
       <(> <Person> <,> , <)+> repeats a hole one or more times,
       separated by commas (<)*> also allows none). The token types
       <NUMBER>, <STRING> and <NAME> accept a
       number, a quoted string or a name. Several alternatives of one type are separated by commas, each
       with its own precedence.

Precedence

    
An operator is a functor whose pattern starts with a hole, like <Expr> plus <Expr>.
       When a sentence contains several operators, their precedence #N decides how they group: the
       higher one binds tighter. With plus at #40 and times at #50,
       one plus two times three is one plus (two times three); operators of equal
       precedence group from the left. An operator without a precedence does not parse at all. A hole can
       carry a precedence too: <Expr#45> takes only operators above 45, so times
       but not plus. A hole without one takes the precedence of its functor; that is why the
       #0 of a sentence lets every operator in. The standard operators range from #16
       (<->) to #80 (unary -).

Parentheses

    
Parentheses override precedence: (one plus two) times three. You never declare them:
       nelumbo.lang ends with Type P and P ::= (<P>) @nelumbo.lang.Parenthesized,

       a functor to a Java class; Parenthesized returns the expression inside, so (one)
       is just one, not a new phrase. A parenthesized expression is complete in itself, so it fits a
       hole of any precedence: twice (one plus two) parses where twice one plus two did not.

Connected tokens

    
Whitespace between tokens does not matter: the pattern <NUMBER> : <NUMBER> accepts
       9:30 and 9 : 30 alike. Between <[> and <]> the
       tokens must touch: <[> <NUMBER> : <NUMBER> <]> accepts only 9:30.
       Use it for a literal written as several tokens, such as a time, a date or a decimal number, so that it cannot
       be mistaken for an expression with an operator. <[> and <]> themselves do not
       appear in the sentence. The standard library writes 3.14, 2025-01-01 and
       16#FF this way, and nelumbo.lang the head of a generic type like
       Team<E>.

Scoping

    
A { } block is a scope. A functor declared private in a block exists only
       inside that block, including nested blocks. Without private, a declaration in a block
       stays visible after the block: the block alone hides nothing. Below, Max is private to the
       block and Piet is not. private is also how two functors with the same pattern
       are kept apart: if they are declared side by side, the parser cannot tell them apart and reports a
       non deterministic pattern merge.

Propositional logic

    
This is the first section with queries. A query is an expression followed by
       ?: it asks Nelumbo whether the expression holds. import nelumbo.logic
       provides the values true, false and unknown, and the
       operators & (and), | (or) and ! (not).

    
There is no Run button: Nelumbo evaluates every query as you type and shows its result at the end
       of the line, in a purple label. A long result is cut short; hover over it to see all of it.

    
A result has two sides, [facts][falsehoods]: on the left the answers for which the
       query is true, on the right those for which it is false. An answer is written between parentheses.
       These queries have no variables, so an answer is just (). .. means that a
       side may contain more than it shows. In the results below:

    
    
      
  • [()][] means "true",
    • 
      
  • [][()] means "false",
    • 
      
  • [..][..] means "unknown": nothing is known on either side.
    • 
    

    
Nelumbo is three-valued: a query is true, false or unknown. unknown & true stays
       unknown, but unknown | true is true, whatever the unknown part turns out to be. Try
       changing the queries below.

    

    
After the ? you may write the result you expect, in the same notation as the label:
       true & false ? [][()] expects false. The editor then checks it instead of showing the
       result: a green check mark at the end of the line when the result matches; otherwise the expected
       result is underlined in red and the actual result follows a red cross. Without an expected result
       you just get the purple label. The exercises use this to show when you are done.

Facts & queries

    
Ground truth is asserted with fact. Objects and their functors are declared first
       (Person :: Object introduces a type, Boolean ::= ... a relation),
       then a query binds a variable and enumerates every matching answer. Facts are open: what is
       not asserted is not false, so the trailing .. in [(X=Jan),..] says
       more answers may exist.

    

    

      
Add a fact so that friends(Klaas, Kees) holds.

      

      

    

    
A function value can be asserted too. A function has exactly one value, so its fact is
       closed: after fact age(Piet)=40 the answer is [(a=40)]
       without .., and every other age is false. Statements run top to bottom, and each fact
       or rule only adds knowledge: unknown answers become true or false, open answers grow or close, and
       nothing already proven is withdrawn. Nelumbo is monotonic, and it checks this. A fact can
       never be taken back further down: after fact age(Piet)=40, a later
       fact age(Piet)=22 is an inconsistency, and nothing after it is evaluated. In the same
       way, when a query is asked again further down, its answer must keep everything the earlier answer
       showed and may only add to it. If not, the query reports an inconsistency.
       Only relations and function values can be asserted: fact !friends(Piet, Klaas)
       is an error.

Unique values

    
Facts are open, but a hole can be declared unique with one:
       <Person> lives in <one City> says that a person lives in exactly one city. A fact then
       closes the hole for that person: Piet lives in c ? answers Amsterdam without
       .., and every other city is false. Nothing is asserted for Jan, so his city stays
       unknown, and the other direction stays open: more people may live in Amsterdam. likes
       has no one, so Piet may like other cities too and Utrecht is unknown. A second city for Piet
       would be rejected as an inconsistency. This is also why a function value is closed: both sides of
       = are unique holes.

Rules & recursion

    
A rule <=> defines how a functor is derived. For a function, == gives
       its value directly: fib(n) == e is short for fib(n)=f <=> f=e.
       if attaches a guard to each alternative, and a rule may reference itself to recurse.
       The classic Fibonacci rule has a base case for n<=1 and a recursive step for
       n>1. Ask for a function's value with a function query: fib(7) ?
       introduces its own result variable, so the answer lists the value without a name,
       [(13)][..]. It is the same as fib(7)=r ? with a declared
       Integer r.

Adding a rule adds knowledge just like adding a fact. It can even add only falsehoods: below,
       adult(Jan) is unknown until a rule says that nobody younger than 18 is an adult.
       After that rule adult(Jan) is false, while the fact adult(Piet) still
       holds. The rule is silent where its guard fails, so it takes nothing away. Had Piet been 16, the
       query adult(Piet) ? after the rule would report an inconsistency with the fact.

    

  

  

    
Combining rules

    
Several rules can define one relation; their answers are combined side by side. The first rule says
       that Piet eats what he likes. All its answers are on the facts side:
       [(f=Apple),(f=Pear),..][..]. Its falsehood side is empty but open (..):
       nothing is known to be false yet. The second rule only adds falsehoods: Piet does not eat what he is
       allergic to. It is silent where its guard fails, so it leaves the facts side alone and fills the open
       falsehood side: [(f=Apple),(f=Pear),..][(f=Fish),(f=Nut),..]. Bread is on neither side,
       so it stays unknown. The rules must agree: had Piet also liked nuts, the query would report an
       inconsistency.

Cyclic rules

    
A rule may depend on itself in a cycle. The recursion of fib ends because
       n gets smaller; here nothing gets smaller: a friend of a friend of mine is a friend of mine,
       so to find my friends, Nelumbo needs my friends. It solves such a cycle by iteration. It starts with
       the facts (Jan is a friend of Piet), applies the rule and finds Klaas, a friend of Jan, applies it
       again and finds Kees, and stops when a round adds nothing new. That end point is the
       fixpoint, and its friends are the answer. The rule need not mention the facts: the facts and
       rules of one relation are combined. What the fixpoint does not reach stays unknown, not false: no fact
       mentions Bob, but the facts are open, so Bob is a friend of Piet ? is
       [..][..].

Equality

    
What = means depends on what a phrase is. A functor with arguments, declared for an
       Object type, is a function: double(2) stands for the value a rule or
       fact gives it, so double(2)=4 is true and double(2)=5 is false. Without
       such a rule or fact the value is unknown, so even point(1,2)=point(1,2) is unknown. A
       type declared :: Literal builds values instead: pos(1,2) is the value
       itself, equal to another one exactly when it is built the same way, and it can be the answer to a
       query (q=pos(1,2)). Constants such as Piet are literals too.

Quantifiers

    
E[c](...) (there exists) and A[c](...) (for all) never try every member of
       a type: c only gets values by navigation, from something already known, here
       from Juliana to her children. Without navigation a quantifier gives no answer, even though four
       people are declared. That is a design choice: Person ::= Juliana, ... names some
       people, not all of them. If A[c](age(c)>10) were decided by trying the declared
       people, declaring one more could turn true into false, and Nelumbo never withdraws an answer. So
       navigate: through a fact or rule (pc(Juliana,c)), through =, or through a
       known collection (c in children(Juliana)). Over a closed set such as Juliana's children,
       A can be true and E false; over open facts more children may exist, so only
       finding an example decides. Put the membership in parentheses before ->.

Controlled English

    
A transformation can turn a dictionary into a language. A controlled natural language is a
       fixed set of sentence shapes, filled with words from a dictionary, where each word's entry decides
       how the word may be used. Here noun a dog and noun an owl record every noun
       with its own article, and the transformation gives each entry its own sentences:
       Rex is a dog and is Hoot an owl ?. So Hoot is a owl does not
       parse: after a only dog and cat fit. verb chases
       adds Rex chases Tom and who chases Hoot ?. A sentence becomes a fact and a
       question becomes a query. Nothing says that Tom is not a dog, so is Tom a dog ? is
       unknown. The Dutch example deHet does the same with the articles
       de and het.

Vectors

Expression interpreter

    
A language inside your language: arithmetic expressions with variables, and a function eval
       that computes their value. An expression is a value, a tree of parts: x + #2 equals
       x + #2 but not #2 + x, although both evaluate to 5. eval is a
       function over those trees, with one rule per kind of expression. The variables get their values from
       facts, and a variable without a value gives an unknown result, not an error.

    

      Hints
      
    
        
  1. Declare Expr :: Object, and Var :: Expr with the constants x,
            y and z.
    2. 
        
  2. Declare the other expressions as literals so that an expression is a value:
            {Literal,Expr} ::= # <Integer> #90, <Expr> + <Expr> #40,
            <Expr> * <Expr> #50. The types of the operands tell x + #2 apart from
            3 + 2.
    3. 
        
  3. Declare eval <Expr> as an Integer function with #80, and
            <Var> := <one Integer> as a Boolean phrase with #20:
            a variable has one value.
    4. 
        
  4. Write one rule per kind of expression, with a head that takes it apart:
            eval (e + f) == eval e + eval f. A variable's value comes from its fact:
            eval v = i <=> v := i.
    5. 
        
  5. Do not declare Expr :: Literal: a functor whose holes all have literal types is a
            constructor, so eval would become one too.

Room booking

    
Today's bookings for a few meeting rooms are given with times like 9:30. Answer whether a
       room is free, at a time or between two times, and whether a room's bookings clash. "Free" is the hard
       part. In an open world you can prove that a room is taken: you find the booking. Proving that it is free requires
       every booking for the room, so each room's bookings are given as one complete set. Yellow has
       no set, so whether it is free stays unknown.

    

      Hints
      
    
        
  1. A time is a named pattern of connected tokens, so 9:30 parses and 9 : 30
            does not: pattern TIME ::= <[> <Integer#100> : <Integer#100> <]>.
            In a phrase, <TIME> gives two Integer arguments, hours and minutes; compare times
            in minutes, h*60+m.
    2. 
        
  2. A booking is a value, not a fact: declare Slot :: Literal with the pattern
            <TIME> to <TIME> (precedence #35), and
            the bookings for <Room> as a function that returns a Set<Slot>
            (precedence #60).
    3. 
        
  3. Because each set is complete, A[b]((b in the bookings for r) -> ...) can be true.
    4. 
        
  4. For relations about a slot, such as <Integer> falls in <Slot>, let the rule
            head take the slot apart: n falls in h1:m1 to h2:m2 <=> ....
    5. 
        
  5. A room is free between two times when it is free at the first, and no booking starts at or after the first
            and before the second.
    6. 
        
  6. Bookings clash when one starts during another. A booking does not clash with itself
            (!=).
    7.

Access policy

    
A policy language for who may do what. A dictionary lists every role with its article, and the policy
       is written as plain statements: every manager may approve invoices, no intern may
       approve invoices. Transformations turn every statement into a fact or a rule. Allow rules fill the
       facts side of an answer, deny rules the falsehood side. Where no policy applies, the answer is unknown,
       not denied: nothing says whether Eva, an auditor, may approve invoices. When you are done, add
       Ann is a manager: she is then both allowed and denied, and Nelumbo reports the
       inconsistency instead of picking one.

    

      Hints
      
    
        
  1. Declare the types Person, Role, Action and Item with
            their constants, and an Article type with a and an.
    2. 
        
  2. Only <Person> may <Action> <Item> is a question: a Boolean
            phrase with precedence #30. The other lines are statements: Root phrases
            with precedence #0, and role <Article> <Role> with
            #100.
    3. 
        
  3. Store a person's roles in a relation of your own, for example a private
            <Person> has role <Role>.
    4. 
        
  4. A dictionary entry such as role an intern is transformed, as in Controlled English: it
            declares the sentences with that article, <Person> is an intern and
            every <Role> is an intern, and transformations for them. The first adds a fact,
            the second a rule: whoever has the one role has the other.
    5. 
        
  5. A policy statement is transformed into a rule: every r may x i into
            q may x i <=> true if q has role r, no r may x i into the same with
            false.
    6. 
        
  6. In a transformation, use variables such as {Role,Literal} r in the heads, and give
            every functor declared in a transformation body at least one hole (a known engine bug).
    7. 
      

    

    

      
Write the language above the given part so that the dictionary, the policy and the staff parse and every question gets the expected answer.
