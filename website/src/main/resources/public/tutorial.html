Types & functors

Before any logic, Nelumbo lets you define syntax: which phrases exist and how they are built. Person :: Object declares a type and Male :: Person a subtype. Male ::= Piet, Jan declares constants of a type. A functor declares a new phrase with ::=: Person ::= father(<Person>) says that father(a person) is itself a person, where each <T> is a hole for an expression of type T. A phrase whose type extends Root can stand on its own line as a sentence; give such a functor the precedence #0. These sections have no queries and no meaning yet: a sentence is correct when it parses, and the editor underlines it in red when it does not.

import nelumbo.lang Person :: Object Male :: Person Female :: Person Male ::= Piet, Jan Female ::= Marie Person ::= father(<Person>) Sentence :: Root Sentence ::= <Person> knows <Person> #0 Piet knows Marie father(Marie) knows Jan

Marie knows Klaas does not parse: Klaas is declared as an Animal, and knows takes a Person. Klaas is a man: fix the declarations so the sentence parses.

import nelumbo.lang Person :: Object Male :: Person Female :: Person Animal :: Object Male ::= Piet, Jan Female ::= Marie Animal ::= Klaas Sentence :: Root Sentence ::= <Person> knows <Person> #0 Marie knows Klaas 
import nelumbo.lang
Person   :: Object
Male     :: Person
Female   :: Person
Animal   :: Object
Male     ::= Piet, Jan, Klaas
Female   ::= Marie
Sentence :: Root
Sentence ::= <Person> knows <Person> #0
Marie knows Klaas

Declare a type Thing with the constants flowers and a book, and a functor, so that both sentences parse.

import nelumbo.lang Person :: Object Person ::= Piet, Marie Sentence :: Root // declare a type Thing, its constants and a sentence functor so both sentences parse Marie gives flowers to Piet Piet gives a book to Marie 
import nelumbo.lang

Person   ::= Piet, Marie
Thing    :: Object
Thing    ::= flowers, a book
Sentence :: Root
Sentence ::= <Person> gives <Thing> to <Person> #0
Marie gives flowers to Piet
Piet gives a book to Marie

Patterns

A functor's pattern is more than words and holes. <(> really <)?> is optional, <(> likes <|> loves <)> is a choice, and <(> <Person> <,> , <)+> repeats a hole one or more times, separated by commas (<)*> also allows none). The token types <NUMBER>, <STRING> and <NAME> accept a number, a quoted string or a name. Several alternatives of one type are separated by commas, each with its own precedence.

import nelumbo.lang Person :: Object Person ::= Piet, Jan, Marie, Klaas Sentence :: Root Sentence ::= <Person> <(> really <)?> <(> likes <|> loves <)> <Person> #0, <Person> is <NUMBER> years old #0, <Person> says <STRING> #0, party with <(> <Person> <,> , <)+> #0 Piet likes Marie Piet really loves Marie Klaas is 42 years old Marie says "hello" party with Piet, Jan, Marie

Piet can invite any number of guests, with and before the last one. Change the pattern so all three sentences parse.

import nelumbo.lang Person :: Object Person ::= Piet, Jan, Marie, Klaas Sentence :: Root // change the pattern so all three sentences parse Sentence ::= <Person> invites <Person> #0 Piet invites Jan Piet invites Jan and Marie Piet invites Jan, Marie and Klaas 
import nelumbo.lang
Person   :: Object
Person   ::= Piet, Jan, Marie, Klaas
Sentence :: Root
Sentence ::= <Person> invites <(> <Person> <,> , <)+> <(> and <Person> <)?> #0
Piet invites Jan
Piet invites Jan and Marie
Piet invites Jan, Marie and Klaas

Change the pattern so that Jan does not know Piet parses as well as Jan knows Piet.

import nelumbo.lang Person :: Object Person ::= Piet, Jan Sentence :: Root // change the pattern so both sentences parse Sentence ::= <Person> knows <Person> #0 Jan knows Piet Jan does not know Piet

Precedence

An operator is a functor whose pattern starts with a hole, like <Expr> plus <Expr>. When a sentence contains several operators, their precedence #N decides how they group: the higher one binds tighter. With plus at #40 and times at #50, one plus two times three is one plus (two times three); operators of equal precedence group from the left. An operator without a precedence does not parse at all. A hole can carry a precedence too: <Expr#45> takes only operators above 45, so times but not plus. A hole without one takes the precedence of its functor; that is why the #0 of a sentence lets every operator in. The standard operators range from #16 (<->) to #80 (unary -).

import nelumbo.lang Expr :: Object Expr ::= one, two, three Expr ::= <Expr> plus <Expr> #40, <Expr> times <Expr> #50 Sentence :: Root Sentence ::= compute <Expr> #0, twice <Expr#45> #0 // one plus (two times three) compute one plus two times three // (one times two) plus three compute one times two plus three twice two times three

minus has no precedence, so the last sentence does not parse. Give it the precedence of plus.

import nelumbo.lang Expr :: Object Expr ::= one, two, three // give minus a precedence, the same as plus Expr ::= <Expr> plus <Expr> #40, <Expr> minus <Expr>, <Expr> times <Expr> #50 Sentence :: Root Sentence ::= compute <Expr> #0 compute three minus one times two 
import nelumbo.lang

Expr     ::= one, two, three
Expr     ::= <Expr> plus <Expr>  #40,
             <Expr> minus <Expr> #40,
             <Expr> times <Expr> #50
Sentence :: Root
Sentence ::= compute <Expr> #0

twice one plus two does not parse: the hole <Expr#45> rejects plus. Change only the precedence of the hole so both sentences parse.

import nelumbo.lang Expr :: Object Expr ::= one, two, three Expr ::= <Expr> plus <Expr> #40, <Expr> times <Expr> #50 Sentence :: Root // change only the precedence of the hole so both sentences parse Sentence ::= twice <Expr#45> #0 twice two times three twice one plus two

Parentheses

Parentheses override precedence: (one plus two) times three. You never declare them: nelumbo.lang ends with Type P and P ::= (<P>) @nelumbo.lang.Parenthesized, one generic functor (see the next section) that gives every type its parentheses. The @ binds a functor to a Java class; Parenthesized returns the expression inside, so (one) is just one, not a new phrase. A parenthesized expression is complete in itself, so it fits a hole of any precedence: twice (one plus two) parses where twice one plus two did not.

import nelumbo.lang Expr :: Object Expr ::= one, two, three Expr ::= <Expr> plus <Expr> #40, <Expr> times <Expr> #50 Person :: Object Person ::= Piet, Marie Person ::= father(<Person>) Sentence :: Root Sentence ::= compute <Expr> #0, twice <Expr#45> #0, <Person> knows <Person> #0 compute (one plus two) times three twice (one plus two) twice ((one)) (father(Marie)) knows (Piet)

Add square brackets as a second way to group expressions so that the last sentence parses. Bind them to @nelumbo.lang.Parenthesized too, so that [one] is just one.

import nelumbo.lang Expr :: Object Expr ::= one, two, three Expr ::= <Expr> plus <Expr> #40, <Expr> times <Expr> #50 // add square brackets as a second way to group expressions Sentence :: Root Sentence ::= compute <Expr> #0 compute (one plus two) times three compute [one plus two] times three 
import nelumbo.lang
Expr     :: Object
Expr     ::= one, two, three
Expr     ::= <Expr> plus <Expr>  #40,
             <Expr> times <Expr> #50
Expr     ::= [<Expr>] @nelumbo.lang.Parenthesized
Sentence :: Root
Sentence ::= compute <Expr> #0
compute (one plus two) times three
compute [one plus two] times three

Generics

Type E declares a type parameter. With it, Team<E> :: Object declares a generic type and Team<E> ::= team of <(> <E> <,> , <)+> a functor for it: team of Piet, Jan is a Team<Person> and team of Rex, Tom a Team<Animal>. A hole names the kind of team it takes: <Team<Person>> rejects a team of animals, <Team<E>> takes a team of anything. Write a generic type without spaces: Team<E>, not Team < E >. The parentheses of the previous section are declared this way, and so are the collection types List<E> and Set<E>.

import nelumbo.lang Person :: Object Person ::= Piet, Jan, Marie Animal :: Object Animal ::= Rex, Tom, Bello Type E Team<E> :: Object Team<E> ::= team of <(> <E> <,> , <)+> Sentence :: Root Sentence ::= <Team<Person>> plays against <Team<Person>> #0, <Team<Animal>> chases <Team<Animal>> #0 team of Piet, Jan plays against team of Marie team of Rex chases team of Tom, Bello

A team can only hold people, so the last sentence does not parse. Make Team generic so that animals can form teams too.

import nelumbo.lang Person :: Object Person ::= Piet, Jan, Marie Animal :: Object Animal ::= Rex, Tom, Bello // make Team generic, so that animals can form teams too Team :: Object Team ::= team of <(> <Person> <,> , <)+> Sentence :: Root Sentence ::= <Team> plays against <Team> #0 team of Piet, Jan plays against team of Marie team of Rex plays against team of Tom, Bello

Connected tokens

Whitespace between tokens does not matter: the pattern <NUMBER> : <NUMBER> accepts 9:30 and 9 : 30 alike. Between <[> and <]> the tokens must touch: <[> <NUMBER> : <NUMBER> <]> accepts only 9:30. Use it for a literal written as several tokens, such as a time, a date or a decimal number, so that it cannot be mistaken for an expression with an operator. <[> and <]> themselves do not appear in the sentence. The standard library writes 3.14, 2025-01-01 and 16#FF this way, and nelumbo.lang the head of a generic type like Team<E>.

import nelumbo.lang Person :: Object Person ::= Piet, Marie Time :: Object Time ::= <[> <NUMBER> : <NUMBER> <]> Sentence :: Root Sentence ::= <Person> arrives at <Time> #0 Piet arrives at 9:30 Marie arrives at 14:05 // Piet arrives at 9 : 30 does not parse

Declare a type Date for dates like 1990-05-17, written without spaces, so that both sentences parse.

import nelumbo.lang Person :: Object Person ::= Piet, Marie Time :: Object Time ::= <[> <NUMBER> : <NUMBER> <]> // declare the type Date, with connected tokens like Time Sentence :: Root Sentence ::= <Person> arrives at <Time> #0, <Person> was born on <Date> #0 Piet arrives at 9:30 Marie was born on 1990-05-17 
import nelumbo.lang

Person   ::= Piet, Marie
Time     :: Object
Time     ::= <[> <NUMBER> : <NUMBER> <]>
Date     :: Object
Date     ::= <[> <NUMBER> - <NUMBER> - <NUMBER> <]>
Sentence :: Root
Sentence ::= <Person> arrives at <Time>   #0,
             <Person> was born on <Date> #0

Named patterns

A recurring piece of a pattern can be given a name: pattern GUESTS ::= ... declares it, and <GUESTS> stands for its body wherever it is used after the declaration. A named pattern is just an abbreviation: unlike a functor, it declares no type and builds no value. Here GUESTS is the guest list of the Patterns exercise, now shared by two sentences. nelumbo.lang uses named patterns itself, for instance pattern QNAME ::= <[> <(> <NAME> <,> . <)+> <]> for the dotted name after import.

import nelumbo.lang Person :: Object Person ::= Piet, Jan, Marie, Klaas pattern GUESTS ::= <(> <Person> <,> , <)+> <(> and <Person> <)?> Sentence :: Root Sentence ::= <Person> invites <GUESTS> #0, party with <GUESTS> #0 Piet invites Jan, Marie and Klaas party with Jan and Marie

Both sentences use <TIME>, which is not declared yet. Declare it as a named pattern for a time like 9:30, above the functor that uses it.

import nelumbo.lang Person :: Object Person ::= Piet, Marie, Klaas // declare the named pattern TIME, for a time like 9:30 Sentence :: Root Sentence ::= <Person> arrives at <TIME> #0, <Person> works from <TIME> to <TIME> #0 Marie arrives at 9:30 Klaas works from 8:00 to 17:30 
import nelumbo.lang
Person   :: Object
Person   ::= Piet, Marie, Klaas
pattern TIME ::= <[> <NUMBER> : <NUMBER> <]>
Sentence :: Root
Sentence ::= <Person> arrives at <TIME>          #0,
             <Person> works from <TIME> to <TIME> #0
Marie arrives at 9:30

Scoping

A { } block is a scope. A functor declared private in a block exists only inside that block, including nested blocks. Without private, a declaration in a block stays visible after the block: the block alone hides nothing. Below, Max is private to the block and Piet is not. private is also how two functors with the same pattern are kept apart: if they are declared side by side, the parser cannot tell them apart and reports a non deterministic pattern merge.

import nelumbo.lang Person :: Object Sentence :: Root Sentence ::= <Person> reads #0 { private Person ::= Max Person ::= Piet Max reads { Max reads } } Piet reads // Max reads does not parse here: Max is private to the block

Both functors are written friend(<Person>), one for a person and one for a dog, so they clash. Restrict each one to the sentence that uses it so that both sentences parse.

import nelumbo.lang Person :: Object Dog :: Object Person ::= Piet, Marie Sentence :: Root Sentence ::= <Person> reads #0, <Dog> barks #0 // these two functors clash: restrict each to the sentence that uses it Person ::= friend(<Person>) Dog ::= friend(<Person>) friend(Marie) reads friend(Piet) barks 
import nelumbo.lang
Person   :: Object
Dog      :: Object
Person   ::= Piet, Marie
Sentence :: Root
Sentence ::= <Person> reads #0,
             <Dog> barks    #0
{
    private Person ::= friend(<Person>)
    friend(Marie) reads
}
{
    private Dog ::= friend(<Person>)
    friend(Piet) barks
}

Rex is private to its block, so the last sentence does not parse. Make it parse without moving it.

import nelumbo.lang Person :: Object Dog :: Object Sentence :: Root Sentence ::= <Person> reads #0, <Dog> barks #0 { private Person ::= Max Max reads } { private Dog ::= Rex Rex barks } // make this sentence parse, without moving it Rex barks 
import nelumbo.lang
Person   :: Object
Dog      :: Object
Sentence :: Root
Sentence ::= <Person> reads #0,
             <Dog> barks    #0
{
    private Person ::= Max
    Max reads
}
{
    Dog ::= Rex
    Rex barks
}
Rex barks

Propositional logic

This is the first section with queries. A query is an expression followed by ?: it asks Nelumbo whether the expression holds. import nelumbo.logic provides the values true, false and unknown, and the operators & (and), | (or) and ! (not).

There is no Run button: Nelumbo evaluates every query as you type and shows its result at the end of the line, in a purple label. A long result is cut short; hover over it to see all of it.

A result has two sides, [facts][falsehoods]: on the left the answers for which the query is true, on the right those for which it is false. An answer is written between parentheses. These queries have no variables, so an answer is just (). .. means that a side may contain more than it shows. In the results below:

  • [()][] means "true",
  • [][()] means "false",
  • [..][..] means "unknown": nothing is known on either side.

Nelumbo is three-valued: a query is true, false or unknown. unknown & true stays unknown, but unknown | true is true, whatever the unknown part turns out to be. Try changing the queries below.

import nelumbo.logic true & true ? true & false ? true | false ? !false ? unknown & true ? unknown | true ?

After the ? you may write the result you expect, in the same notation as the label: true & false ? [][()] expects false. The editor then checks it instead of showing the result: a green check mark at the end of the line when the result matches; otherwise the expected result is underlined in red and the actual result follows a red cross. Without an expected result you just get the purple label. The exercises use this to show when you are done.

Make the query below come out true by changing only the operator.

import nelumbo.logic false & true ? [()][] 
import nelumbo.logic

false | true ? [()][]

Facts & queries

Ground truth is asserted with fact. Objects and their functors are declared first (Person :: Object introduces a type, Boolean ::= ... a relation), then a query binds a variable and enumerates every matching answer. Facts are open: what is not asserted is not false, so the trailing .. in [(X=Jan),..] says more answers may exist.

import nelumbo.logic Person :: Object Boolean ::= friends(<Person>,<Person>) Person ::= Piet, Jan, Klaas fact friends(Piet, Jan), friends(Jan, Klaas) Person X friends(Piet, X) ?

Add a fact so that friends(Klaas, Kees) holds.

import nelumbo.logic Person :: Object Boolean ::= friends(<Person>,<Person>) Person ::= Piet, Jan, Klaas, Kees // add a fact here friends(Klaas, Kees) ? [()][] 
import nelumbo.logic
Person :: Object
Boolean ::= friends(<Person>,<Person>)
Person ::= Piet, Jan, Klaas, Kees
fact friends(Klaas, Kees)
friends(Klaas, Kees) ? [()][]

A function value can be asserted too. A function has exactly one value, so its fact is closed: after fact age(Piet)=40 the answer is [(a=40)] without .., and every other age is false. Statements run top to bottom, and each fact or rule only adds knowledge: unknown answers become true or false, open answers grow or close, and nothing already proven is withdrawn. Nelumbo is monotonic, and it checks this. A fact can never be taken back further down: after fact age(Piet)=40, a later fact age(Piet)=22 is an inconsistency, and nothing after it is evaluated. In the same way, when a query is asked again further down, its answer must keep everything the earlier answer showed and may only add to it. If not, the query reports an inconsistency. Only relations and function values can be asserted: fact !friends(Piet, Klaas) is an error.

import nelumbo.integers Person :: Object Person ::= Piet, Jan Integer ::= age(<Person>) Integer a age(Piet)=a ? fact age(Piet)=40 age(Piet)=a ? age(Piet)=41 ?

Give Jan an age so that both queries below hold.

import nelumbo.integers Person :: Object Person ::= Piet, Jan Integer ::= age(<Person>) Integer a // add a fact here age(Jan)=a ? [(a=35)][..] age(Jan)=40 ? [][()] 
import nelumbo.integers
Person :: Object
Person ::= Piet, Jan
Integer ::= age(<Person>)
Integer a
fact age(Jan)=35
age(Jan)=a  ? [(a=35)][..]
age(Jan)=40 ? [][()]

Unique values

Facts are open, but a hole can be declared unique with one: <Person> lives in <one City> says that a person lives in exactly one city. A fact then closes the hole for that person: Piet lives in c ? answers Amsterdam without .., and every other city is false. Nothing is asserted for Jan, so his city stays unknown, and the other direction stays open: more people may live in Amsterdam. likes has no one, so Piet may like other cities too and Utrecht is unknown. A second city for Piet would be rejected as an inconsistency. This is also why a function value is closed: both sides of = are unique holes.

import nelumbo.logic Person :: Object Person ::= Piet, Jan City :: Object City ::= Amsterdam, Utrecht Boolean ::= <Person> lives in <one City> #30, <Person> likes <City> #30 City c Person p fact Piet lives in Amsterdam fact Piet likes Amsterdam Piet lives in c ? Piet lives in Utrecht ? Jan lives in c ? p lives in Amsterdam ? Piet likes c ? Piet likes Utrecht ?

[(c=Utrecht)][..] Jan was born in Amsterdam ? [][()]

Rules & recursion

A rule <=> defines how a functor is derived. For a function, == gives its value directly: fib(n) == e is short for fib(n)=f <=> f=e. if attaches a guard to each alternative, and a rule may reference itself to recurse. The classic Fibonacci rule has a base case for n<=1 and a recursive step for n>1. Ask for a function's value with a function query: fib(7) ? introduces its own result variable, so the answer lists the value without a name, [(13)][..]. It is the same as fib(7)=r ? with a declared Integer r.

import nelumbo.integers Integer ::= fib(<Integer>) Integer n fib(n) == n if n<=1, fib(n-1)+fib(n-2) if n>1 fib(7) ?

Define factorial so that factorial(5) = 120.

import nelumbo.integers Integer ::= factorial(<Integer>) Integer n // fix this rule so factorial(5)=120 (hint: 1 if n<=0, else n*factorial(n-1)) factorial(n) == n factorial(5) ? [(120)][..] 
import nelumbo.integers
Integer ::= factorial(<Integer>)
Integer n
factorial(n) == 1 if n<=0, n*factorial(n-1) if n>0
factorial(5) ? [(120)][..]

Adding a rule adds knowledge just like adding a fact. It can even add only falsehoods: below, adult(Jan) is unknown until a rule says that nobody younger than 18 is an adult. After that rule adult(Jan) is false, while the fact adult(Piet) still holds. The rule is silent where its guard fails, so it takes nothing away. Had Piet been 16, the query adult(Piet) ? after the rule would report an inconsistency with the fact.

import nelumbo.integers Person :: Object Person ::= Piet, Jan Integer ::= age(<Person>) Boolean ::= adult(<Person>) Person p fact age(Piet)=40, age(Jan)=12 fact adult(Piet) adult(Piet) ? [()][] adult(Jan) ? [..][..] // unknown: no fact, no rule adult(p) <=> false if age(p)<18 adult(Piet) ? [()][] // unchanged adult(Jan) ? [][()] // now false: only the falsehood side grew

Combining rules

Several rules can define one relation; their answers are combined side by side. The first rule says that Piet eats what he likes. All its answers are on the facts side: [(f=Apple),(f=Pear),..][..]. Its falsehood side is empty but open (..): nothing is known to be false yet. The second rule only adds falsehoods: Piet does not eat what he is allergic to. It is silent where its guard fails, so it leaves the facts side alone and fills the open falsehood side: [(f=Apple),(f=Pear),..][(f=Fish),(f=Nut),..]. Bread is on neither side, so it stays unknown. The rules must agree: had Piet also liked nuts, the query would report an inconsistency.

import nelumbo.logic Person :: Object Person ::= Piet Food :: Object Food ::= Apple, Pear, Nut, Fish, Bread Boolean ::= likes(<Person>,<Food>), allergic(<Person>,<Food>), eats(<Person>,<Food>) Person p Food f fact likes(Piet, Apple), likes(Piet, Pear) fact allergic(Piet, Nut), allergic(Piet, Fish) eats(p,f) <=> likes(p,f) eats(Piet,f) ? eats(p,f) <=> false if allergic(p,f) eats(Piet,f) ? eats(Piet,Bread) ?

Piet invites his friends, but nothing says whom he does not invite. Add a second rule so that nobody invites someone they quarrel with, and the falsehood side fills up.

import nelumbo.logic Person :: Object Person ::= Piet, Jan, Klaas, Kees, Bob Boolean ::= friends(<Person>,<Person>), quarrels(<Person>,<Person>), invites(<Person>,<Person>) Person p, q fact friends(Piet, Jan), friends(Piet, Klaas) fact quarrels(Piet, Kees), quarrels(Piet, Bob) invites(p,q) <=> friends(p,q) // add a rule: nobody invites someone they quarrel with invites(Piet,q) ? [(q=Jan),(q=Klaas),..][(q=Bob),(q=Kees),..] 
import nelumbo.logic
Person  :: Object
Person  ::= Piet, Jan, Klaas, Kees, Bob
Boolean ::= friends(<Person>,<Person>), quarrels(<Person>,<Person>), invites(<Person>,<Person>)
Person  p, q
fact friends(Piet, Jan), friends(Piet, Klaas)
fact quarrels(Piet, Kees), quarrels(Piet, Bob)
invites(p,q) <=> friends(p,q)

Cyclic rules

A rule may depend on itself in a cycle. The recursion of fib ends because n gets smaller; here nothing gets smaller: a friend of a friend of mine is a friend of mine, so to find my friends, Nelumbo needs my friends. It solves such a cycle by iteration. It starts with the facts (Jan is a friend of Piet), applies the rule and finds Klaas, a friend of Jan, applies it again and finds Kees, and stops when a round adds nothing new. That end point is the fixpoint, and its friends are the answer. The rule need not mention the facts: the facts and rules of one relation are combined. What the fixpoint does not reach stays unknown, not false: no fact mentions Bob, but the facts are open, so Bob is a friend of Piet ? is [..][..].

import nelumbo.logic Person :: Object Person ::= Piet, Jan, Klaas, Kees, Bob Boolean ::= <Person> is a friend of <Person> #30 Person me, f, ff, Who // a friend of a friend of mine is a friend of mine ff is a friend of me <=> E[f](ff is a friend of f & f is a friend of me) fact Jan is a friend of Piet fact Klaas is a friend of Jan fact Kees is a friend of Klaas Who is a friend of Piet ? Kees is a friend of Piet ? Bob is a friend of Piet ?

Friendship goes both ways: if Jan is a friend of Piet, Piet is a friend of Jan. Extend the rule so the expected results hold. Through Jan, Piet then turns out to be a friend of himself.

import nelumbo.logic Person :: Object Person ::= Piet, Jan, Klaas, Kees Boolean ::= <Person> is a friend of <Person> #30 Person me, f, ff, Who // friendship goes both ways: extend the rule ff is a friend of me <=> E[f](ff is a friend of f & f is a friend of me) fact Jan is a friend of Piet fact Klaas is a friend of Jan fact Kees is a friend of Klaas Piet is a friend of Kees ? [()][] Piet is a friend of Piet ? [()][] Who is a friend of Piet ? [(Who=Jan),(Who=Kees),(Who=Klaas),(Who=Piet),..][..]

Data types

Nelumbo ships with built-in types - integers, rationals, strings, collections, datetime - each importable, with its own operators and functions. Declare a variable of a type, then let a query compute and bind it. Operators like + and functions like len come from the imported module.

import nelumbo.integers import nelumbo.strings Integer i String s 2+3=i ? "foo"+"bar"=s ? len("hello")=i ?

Quantifiers

E[c](...) (there exists) and A[c](...) (for all) never try every member of a type: c only gets values by navigation, from something already known, here from Juliana to her children. Without navigation a quantifier gives no answer, even though four people are declared. That is a design choice: Person ::= Juliana, ... names some people, not all of them. If A[c](age(c)>10) were decided by trying the declared people, declaring one more could turn true into false, and Nelumbo never withdraws an answer. A transformation can turn a dictionary into a language. Room booking

Today's bookings for a few meeting rooms are given with times like 9:30. Answer whether a room is free, at a time or between two times, and whether a room's bookings clash. "Free" is the hard part. In an open world you can prove that a room is taken: you find the booking. Proving that it is free requires every booking for the room, so each room's bookings are given as one complete set. Yellow has no set, so whether it is free stays unknown.

Hints
  1. A time is a named pattern of connected tokens, so 9:30 parses and 9 : 30 does not: pattern TIME ::= <[> <Integer#100> : <Integer#100> <]>. In a phrase, <TIME> gives two Integer arguments, hours and minutes; compare times in minutes, h*60+m.
  2. A booking is a value, not a fact: declare Slot :: Literal with the pattern <TIME> to <TIME> (precedence #35), and the bookings for <Room> as a function that returns a Set<Slot> (precedence #60).
  3. Because each set is complete, A[b]((b in the bookings for r) -> ...) can be true.
  4. For relations about a slot, put the Integer first: <Integer> falls in <Slot>, and let the rule head take the slot apart: n falls in h1:m1 to h2:m2 <=> .... A phrase that starts with a Slot hole runs into a known engine bug.
  5. A room is free between two times when it is free at the first, and no booking starts at or after the first and before the second.
  6. Bookings clash when one starts during another. A booking does not clash with itself (!=).

Access policy

A policy language for who may do what. A dictionary lists every role with its article, and the policy is written as plain statements: every manager may approve invoices, no intern may approve invoices. Transformations turn every statement into a fact or a rule. Allow rules fill the facts side of an answer, deny rules the falsehood side. Where no policy applies, the answer is unknown, not denied: nothing says whether Eva, an auditor, may approve invoices. When you are done, add Ann is a manager: she is then both allowed and denied, and Nelumbo reports the inconsistency instead of picking one.

Hints
  1. Declare the types Person, Role, Action and Item with their constants, and an Article type with a and an.
  2. Only <Person> may <Action> <Item> is a question: a Boolean phrase with precedence #30. The other lines are statements: Root phrases with precedence #0, and role <Article> <Role> with #100.
  3. Store a person's roles in a relation of your own, for example a private <Person> has role <Role>.
  4. A dictionary entry such as role an intern is transformed, as in Controlled English: it declares the sentences with that article, <Person> is an intern and every <Role> is an intern, and transformations for them. The first adds a fact, the second a rule: whoever has the one role has the other.
  5. A policy statement is transformed into a rule: every r may x i into q may x i <=> true if q has role r, no r may x i into the same with false.
  6. In a transformation, use variables such as {Role,Literal} r in the heads, and give every functor declared in a transformation body at least one hole (a known engine bug).
